## Memory finding in their code (affects the pod)

The first G4 run was OOM-killed at **25.7 GB** after 6 prompts. Cause: their gate hook (`attributors.py`
`generate_attribution_score_filter_hook`) keeps the candidate tensor `v` in a closure that the tensor's own autograd
graph references through the HookPoint's full backward hook: a reference cycle through C++ that Python's gc cannot
free, ~120 MB per hierarchical pass at T = 16 (measured; ungated and masked passes do not leak). Glue in `ge_core.py`
(their code untouched, no value changes):
1. `hier_pass` releases the feature tensors' storage and grads after the pass (a plain torch forward / pre-forward
   hook on each `sae.hook_feature_acts` captures them): 120 → ~5 MB per pass at T = 16.
2. `run_ge.upstream`: only the dictionaries at or before the root's site are spliced. Downstream candidates' ancestors
   are never run by the backward from the root, so their saved activations were kept by the cycle (peak 14.3 GB for 6
   circuits at T ≤ 64). Exact: the smoke re-run with it is **bitwise identical** to the all-24 run (node sets,
   attributions, leaf parts, post-hoc counts; `check_ge_smoke.py`), and peak RSS fell to 9.7 GB.
3. `maybe_reexec`: past `--max-rss-gb` (default 9) the process re-executes itself and resumes (the residual leak is
   ~0.5 GB per deep circuit at T = 64). On the pod (GPU) the residual leak is VRAM, so keep the re-exec on.

## A6: `make_targets.py` (.venv)

Rule (docstring): 24 slots = 12 layers × {tc, z} (z slots at L5 / L7 include `z2`), 2 per slot; frame = latents with
top 64 / 64 and mid ≥ 48 / 64, sorted then shuffled by one `random.Random(20261105)`; accept = the driver's own record
(`Runner.contexts`, group split) with a strong pool, ≥ 8 held strongest, ≥ 32 contrast, ≥ K = 8 strong training
contexts; prompts = the K highest-peak contexts of the strong part of the WCM training arm, truncated after the anchor,
no BOS (the baselines prepend it; root = anchor + 1); held-out = the record's sets via the driver's `manifest()`.
Outputs: `ctx/` (the driver's CTX_DIR), `select.jsonl`, `targets.txt`, `prompts.jsonl`, `targets.json`,
`MANIFEST.json` (md5 of every output + input store sizes + data-pass manifest md5).

by its first 2 candidates** (no rejects), 15 min CPU, 7.2 GB. **Deterministic**: a full rerun into a fresh directory
gave identical md5 on all 51 files (deleted afterwards). Candidates per slot (tc / z; z = z + z2 at L5, L7):
